# 一、DDL语言核心认知
在正式进入实操环节之前，我们先系统、全面地搞懂DDL语言的核心定位、作用边界，以及它在Python全栈开发中的核心价值，从根源上理解“我们为什么要学DDL、什么时候该用DDL”。

## 1.1 DDL的基础定义
DDL的全称是**Data Definition Language**，中文名为**数据定义语言**，是SQL语言四大核心分类中最基础的一类，它的核心作用是**对数据库、数据表、字段、索引等数据库对象的结构进行定义、创建、修改和删除**，管理的是数据库的「骨架结构」，而非数据库中存储的具体业务数据。

简单来说，DDL是数据库的「工程设计语言」：
- 你要搭建一个Python电商项目，首先需要创建项目专属的数据库，就像给项目建一个专属仓库；
- 要存储用户、商品、订单等业务数据，需要设计并创建对应的数据表，就像在仓库里搭建不同的货架；
- 要给货架划分不同的分层、定义每个分层存放的物品类型，就需要给表定义字段、数据类型和约束；
- 业务迭代时需要新增功能，就要给表新增字段、修改字段属性，就像给货架加层、调整货架大小；
- 废弃的功能对应的表和数据库，需要进行删除清理，就像拆除不用的货架、废弃不用的仓库。

以上所有对数据库、表的「结构」进行的操作，全部都由DDL语言来完成。

## 1.2 DDL与其他SQL分类的核心边界
很多新手会混淆DDL和其他SQL分类的使用场景，这里我们用一张表清晰地划分四大SQL分类的核心边界，彻底搞懂不同场景该用哪一类SQL：
| SQL分类 | 全称         | 核心作用                         | 操作对象                     | 在Python全栈开发中的使用场景                                 |
| ------- | ------------ | -------------------------------- | ---------------------------- | ------------------------------------------------------------ |
| DDL     | 数据定义语言 | 定义、修改、删除数据库对象的结构 | 数据库、表、字段、索引等结构 | 项目初始化建库建表、业务迭代修改表结构、环境搭建库表同步     |
| DML     | 数据操作语言 | 对表中的数据进行增、删、改操作   | 表中的具体业务数据           | 后端接口处理用户提交的数据，比如用户注册、信息修改、订单删除 |
| DQL     | 数据查询语言 | 对表中的数据进行查询、统计、筛选 | 表中的具体业务数据           | 前端页面数据展示、业务数据统计、用户登录信息校验             |
| DCL     | 数据控制语言 | 管理数据库用户、权限、事务       | 数据库用户、权限、事务       | 生产环境数据库权限分配、核心业务事务控制                     |

## 1.3 DDL在Python全栈开发中的核心价值
对于Python全栈开发者来说，DDL是贯穿项目全生命周期的核心技能，它的价值体现在三个核心阶段：
1. **项目初始化阶段**：任何一个Python后端项目，无论是Django、Flask还是FastAPI开发，第一步都是根据业务需求进行数据库设计，通过DDL语句创建项目的数据库、业务表，搭建整个项目的数据存储底座，没有这个底座，后续的接口开发、数据交互都无从谈起。
2. **业务迭代阶段**：项目上线后，随着业务需求的变化，经常需要新增功能、优化原有功能，这就需要通过DDL语句修改表结构，比如新增字段、修改字段类型、新增索引优化查询性能，这是后端开发的日常工作之一。
3. **多环境协同阶段**：项目的开发环境、测试环境、生产环境，需要保证库表结构的一致性，而同步库表结构的核心，就是DDL语句，这是全栈开发者必须掌握的多环境协同技能。

# 二、DDL-数据库操作全解
数据库是MySQL服务中最顶层的容器，一个MySQL服务可以创建多个相互独立的数据库，不同的项目、不同的业务模块，都应该创建独立的数据库进行数据隔离，这是全栈开发的基础规范。本章节我们将全面讲解数据库的四大核心操作：查询、创建、删除、切换，每一个操作都包含完整语法、参数详解、极简示例、注意事项与新手避坑指南。

## 2.1 查询数据库
查询操作是DDL中最安全、最常用的操作，不会对数据库造成任何修改，核心作用是查看当前MySQL服务中的数据库列表、确认当前操作的数据库位置，是所有数据库操作的前置校验步骤。

### 2.1.1 查询所有数据库
#### 完整语法
```sql
SHOW DATABASES;
```

#### 语法说明
这是MySQL固定的查询语法，无额外参数，执行后会返回当前MySQL服务中所有已经存在的数据库列表，包含MySQL自带的系统数据库和用户自建的业务数据库。

#### 极简示例
```sql
-- 查看当前MySQL服务中所有的数据库
SHOW DATABASES;
```

#### 执行结果详解
执行后默认会返回4个MySQL自带的系统核心数据库，这是MySQL正常运行的基础，**新手禁止修改、删除这些数据库**，我们在这里做全面的详解，让新手彻底理解每个系统库的作用：

![在这里插入图片描述](https://i-blog.csdnimg.cn/direct/7c917628d9b54f0fb7bdff659117e29e.png#pic_center)


| 数据库名           | 核心作用详解                                                 | 操作限制                                    |
| ------------------ | ------------------------------------------------------------ | ------------------------------------------- |
| mysql              | MySQL的核心系统库，存储了MySQL的用户账号、权限配置、数据库参数、日志配置等核心元数据 | 绝对禁止修改、删除，否则会导致MySQL服务崩溃 |
| information_schema | 信息元数据库，存储了当前MySQL服务中所有数据库、表、字段、索引的结构定义信息 | 仅支持查询，禁止修改、删除                  |
| performance_schema | 性能监控数据库，存储了MySQL服务运行时的性能指标、资源占用、语句执行耗时等监控数据 | 仅支持查询，禁止修改、删除                  |
| sys                | 系统视图数据库，将performance_schema中的复杂监控数据封装成了易读的视图，方便开发者和运维人员进行数据库性能排查 | 仅支持查询，禁止修改、删除                  |

除了系统数据库，列表中其他的数据库，都是用户自行创建的业务数据库，比如我们后续会创建的`python_full_stack`、`school`等。

### 2.1.2 查询当前所在数据库
#### 完整语法
```sql
SELECT DATABASE();
```

#### 语法说明
这是MySQL内置的函数，执行后会返回当前所在的数据库名称，核心作用是确认我们当前的操作位置，避免后续的表操作执行到错误的数据库中。

#### 极简示例
```sql
-- 查看当前所在的数据库
SELECT DATABASE();
```

#### 执行结果详解
- 若执行后返回`NULL`：代表当前没有选中任何数据库，此时执行表相关的操作会直接报错；

- 若执行后返回具体的数据库名称：代表当前已经处于该数据库中，后续的表操作会默认在这个数据库中执行。

![在这里插入图片描述](https://i-blog.csdnimg.cn/direct/c956495f627149ca88ca3ec19fc2f447.png#pic_center)


#### 全栈开发使用建议
在Python全栈开发中，每次执行表相关的DDL操作前，都建议先执行该语句，确认当前所在的数据库，避免表建错、改到错误的库，这是避免低级错误的核心规范。

## 2.2 创建数据库
创建数据库是Python项目开发的第一步，我们需要为每个独立的项目创建专属的业务数据库，实现不同项目之间的数据隔离，避免不同项目的表混杂在一起，导致维护困难。

### 完整语法
```sql
CREATE DATABASE [IF NOT EXISTS] 数据库名
[DEFAULT CHARSET 字符集名称]
[COLLATE 排序规则名称];
```

### 全参数详解
我们对语法中的每一个参数进行全面、详细的讲解，新手不仅要会写最简语句，还要理解每个参数的作用，写出符合生产规范的建库语句：
| 参数                       | 是否必选                     | 详细作用与使用说明                                           |
| -------------------------- | ---------------------------- | ------------------------------------------------------------ |
| CREATE DATABASE            | 必选                         | 创建数据库的固定关键字，语法固定，不可修改                   |
| IF NOT EXISTS              | 可选，新手与生产环境强烈推荐 | 防报错、防冲突关键字，作用是：仅当该数据库名称不存在时，才执行创建操作；如果该数据库已经存在，会跳过创建操作，不会抛出任何错误。<br>如果不添加该参数，当数据库已存在时，执行语句会直接报错，因此无论是新手练习还是生产环境，都强烈建议添加该参数。 |
| 数据库名                   | 必选                         | 自定义的数据库名称，全栈开发强制规范：<br>1. 仅使用小写英文字母、数字、下划线，禁止使用中文、特殊符号、空格；<br>2. 名称要体现项目/业务属性，比如`python_shop`、`student_manage`，禁止使用无意义的`test`、`db1`等名称；<br>3. 禁止使用MySQL的关键字作为数据库名，比如`create`、`select`、`order`等。 |
| DEFAULT CHARSET 字符集名称 | 可选，生产环境强制指定       | 设置该数据库的默认字符集，后续在该数据库中创建的表，会默认继承该字符集，无需重复指定。<br>全栈开发强制推荐使用`utf8mb4`字符集，原因：<br>1. MySQL默认的`utf8`字符集最多只支持3个字节的UTF-8字符，无法存储emoji表情、生僻汉字；<br>2. `utf8mb4`是完整的UTF-8字符集，支持4个字节的字符，完美兼容所有中文、emoji表情，是目前行业通用的标准字符集。 |
| COLLATE 排序规则名称       | 可选，配合字符集使用         | 设置字符集的排序、比较规则，必须和指定的字符集匹配，最常用的是`utf8mb4_general_ci`，其中`ci`代表Case Insensitive，即大小写不敏感，适合绝大多数业务场景；<br>如果需要大小写敏感的排序，可以使用`utf8mb4_bin`二进制排序规则。 |

### 示例合集
#### 示例1：最简创建语句（新手入门练习用）
```sql
-- 创建一个名为school的数据库，无额外参数
CREATE DATABASE school;
```
![在这里插入图片描述](https://i-blog.csdnimg.cn/direct/d0145bf3fc304bff9adf39b5d1fb1743.png#pic_center)


> 注意：该语句仅适合新手本地练习使用，当`school`数据库已存在时，执行会直接报错，且未指定字符集，会使用MySQL的默认字符集，可能出现中文乱码问题。

#### 示例2：生产级标准创建语句（全栈开发推荐使用）
```sql
-- 创建Python电商项目专属数据库，仅当数据库不存在时创建，指定utf8mb4字符集与通用排序规则
CREATE DATABASE IF NOT EXISTS python_shop
DEFAULT CHARSET utf8mb4
COLLATE utf8mb4_general_ci;
```
![在这里插入图片描述](https://i-blog.csdnimg.cn/direct/2d432249fd584b7da61e7afdba8fe9a9.png#pic_center)


这是Python全栈开发中最标准、最规范的建库语句，既避免了数据库已存在的报错，又提前指定了字符集，从根源上避免了中文乱码、emoji无法存储的问题，符合生产环境的开发规范。

### 新手避坑指南
1. 建库前先通过`SHOW DATABASES;`确认数据库名是否已存在，避免冲突；
2. 严格遵守数据库命名规范，禁止使用中文、特殊符号、关键字；
3. 生产环境必须指定`utf8mb4`字符集，禁止使用默认字符集；
4. 一个项目对应一个独立的数据库，禁止多个项目共用同一个数据库。

## 2.3 删除数据库
删除数据库是高危操作，执行后会直接删除该数据库下的所有数据表、所有业务数据，且**几乎无法恢复**，新手仅可在本地测试环境练习使用，生产环境必须有严格的审批与备份流程，绝对禁止随意执行。

### 完整语法
```sql
DROP DATABASE [IF EXISTS] 数据库名;
```

### 参数详解
| 参数          | 是否必选           | 详细作用与使用说明                                           |
| ------------- | ------------------ | ------------------------------------------------------------ |
| DROP DATABASE | 必选               | 删除数据库的固定关键字，语法固定，不可修改                   |
| IF EXISTS     | 可选，强烈推荐添加 | 防报错关键字，仅当该数据库存在时，才执行删除操作；如果数据库不存在，会跳过删除，不会抛出错误；<br>如果不添加该参数，当数据库不存在时，执行语句会直接报错。 |
| 数据库名      | 必选               | 要删除的数据库名称，执行前必须再三确认名称正确，绝对不能写错。 |

### 极简示例
```sql
-- 安全删除名为test的数据库，仅当数据库存在时执行删除
DROP DATABASE IF EXISTS test;
```

![在这里插入图片描述](https://i-blog.csdnimg.cn/direct/1308f6c16abc42bc9108aa7132cb60ab.png#pic_center)


### 高危操作红线规范（全栈开发必须遵守）

1. **生产环境绝对红线**：生产环境禁止直接执行`DROP DATABASE`语句，除非有完整的业务下线审批、全量数据备份、回滚方案，否则绝对禁止执行；
2. **操作前强制备份**：无论什么环境，删除数据库前必须对该数据库进行全量备份，确认备份可用后再执行删除操作；
3. **权限管控**：生产环境的数据库账号，绝对不能给普通开发者分配删库权限，仅DBA可拥有该权限，从根源上规避误删风险；
4. **新手练习限制**：新手仅可在本地测试环境，删除自己创建的测试数据库，绝对不要操作系统数据库和他人的业务数据库。

## 2.4 使用/切换数据库
我们创建完数据库后，想要对该数据库中的表进行操作，必须先切换到对应的数据库中，指定后续操作的默认数据库，这是所有表操作的前置必备步骤。

### 完整语法
```sql
USE 数据库名;
```

### 语法说明
- 该语句执行成功后，会将指定的数据库设置为当前会话的默认数据库，后续所有的表操作、数据操作，都会默认在这个数据库中执行；
- 可以随时执行该语句切换到其他数据库，无执行次数限制。

### 极简示例
```sql
-- 切换到python_shop数据库，后续的表操作都在该数据库中执行
USE python_shop;

-- 切换到school数据库
USE school;
```

![在这里插入图片描述](https://i-blog.csdnimg.cn/direct/764f77e002d54d0aa18c3a1cd6673f1b.png#pic_center)


### 全栈开发使用建议

1. 每次执行表相关的操作前，先执行`USE 数据库名;`明确指定操作的数据库，再通过`SELECT DATABASE();`确认切换成功，避免操作错库；
2. 在Python代码中操作数据库时，会在连接配置中直接指定默认数据库，无需在代码中频繁执行`USE`语句，这是后续Python与MySQL交互章节会讲解的内容。

# 三、DDL-表操作-查询全解
切换到指定的数据库后，我们就可以对数据库中的数据表进行操作了。本章节我们讲解表的三大核心查询操作，这些操作是开发中最常用的调试、查看、校验表结构的工具，不会对表结构和数据造成任何修改，新手必须熟练掌握。

## 3.1 查询当前数据库中的所有表
### 完整语法
```sql
SHOW TABLES;
```

### 前置要求
执行该语句前，必须先通过`USE 数据库名;`切换到对应的数据库中，否则会直接报错。

### 极简示例
```sql
-- 先切换到school数据库
USE school;
-- 查看school数据库中所有的数据表
SHOW TABLES;
```

![在这里插入图片描述](https://i-blog.csdnimg.cn/direct/868cb614661942b1ab00696cad65386f.png#pic_center)


### 执行结果详解

# 四、MySQL全量数据类型详解
创建数据表的核心，就是为每个字段定义合适的数据类型，数据类型决定了该字段能存储什么样的数据、占用多少存储空间、支持什么样的操作，是表设计的核心基础。如果数据类型选错，会导致数据存储异常、查询性能低下、业务逻辑出错等一系列问题，因此我们必须全面、系统地掌握MySQL的核心数据类型。

MySQL的数据类型主要分为三大类：**数值类型**、**字符串类型**、**日期时间类型**，下面我们对每一类中的所有类型进行全面详解，同时给出Python全栈开发中的选型建议与使用规范，新手不仅要知道有哪些类型，还要知道什么场景该用什么类型。

## 4.1 数值类型
数值类型用于存储数字数据，比如用户ID、年龄、价格、销量、库存、金额等，分为**整数类型**和**浮点/定点数类型**两大类，完整详情如下：

### 4.1.1 整数类型
整数类型用于存储没有小数部分的整数，不同类型的存储空间、取值范围不同，我们按照存储空间从小到大排序，进行全面详解：
| 类型名称    | 存储空间 | 有符号(SIGNED)取值范围   | 无符号(UNSIGNED)取值范围 | 全栈开发选型建议与适用场景                                   |
| ----------- | -------- | ------------------------ | ------------------------ | ------------------------------------------------------------ |
| TINYINT     | 1字节    | -128 ~ 127               | 0 ~ 255                  | **全栈开发高频使用类型**，存储空间最小，适合存储状态值、枚举值、极小范围的整数，比如：<br>- 性别：1=男，2=女，0=保密；<br>- 状态：0=禁用，1=启用；<br>- 年龄：0~120，完全覆盖人类年龄范围；<br>是最节省空间的整数类型，能使用TINYINT的场景，绝对不要用INT。 |
| SMALLINT    | 2字节    | -32768 ~ 32767           | 0 ~ 65535                | 适合存储小范围的整数，比如商品分类ID、订单状态码、考试分数等，取值范围完全覆盖绝大多数枚举、小范围编号场景。 |
| MEDIUMINT   | 3字节    | -8388608 ~ 8388607       | 0 ~ 16777215             | 适合存储中等范围的整数，使用频率较低，绝大多数场景可以用INT替代。 |
| INT/INTEGER | 4字节    | -2147483648 ~ 2147483647 | 0 ~ 4294967295           | **全栈开发最核心、最常用的整数类型**，取值范围极大，最大支持21亿的有符号数，完全覆盖用户ID、商品ID、订单ID、销量、库存、浏览量等99%的业务场景，是整数类型的首选。 |
| BIGINT      | 8字节    | -2^63 ~ 2^63-1           | 0 ~ 2^64-1               | 适合存储极大范围的整数，核心使用场景：<br>- 分布式系统的雪花算法生成的全局唯一ID；<br>- 超大流水号、日志ID；<br>- 超出INT取值范围的超大数字；<br>普通业务场景无需使用，避免浪费存储空间。 |

#### 补充说明：UNSIGNED无符号属性
给整数类型加上`UNSIGNED`属性，代表该字段不允许存储负数，取值范围从0开始，同时正数的取值范围扩大了一倍。
- 适用场景：年龄、销量、库存、浏览量等绝对不会出现负数的字段，推荐加上`UNSIGNED`属性，既扩大了取值范围，又避免了负数数据的异常；
- 语法示例：`age TINYINT UNSIGNED`、`id INT UNSIGNED`。

### 4.1.2 浮点/定点数类型
用于存储带小数部分的数字，比如商品价格、订单金额、重量、精度数据等，分为浮点类型和定点类型，两者的核心区别是精度问题，我们进行全面详解：
| 类型名称     | 存储空间                   | 核心特点                                                     | 精度风险                                                     | 全栈开发选型建议与适用场景                                   |
| ------------ | -------------------------- | ------------------------------------------------------------ | ------------------------------------------------------------ | ------------------------------------------------------------ |
| FLOAT        | 4字节                      | 单精度浮点数，存储空间小，取值范围大                         | 存在精度丢失问题，当数字的精度超过范围时，会进行四舍五入，导致数据不准确 | **全栈开发禁止用于金额、价格存储**，仅适合存储对精度要求不高的非业务关键数据，比如温度、湿度、距离等传感器数据。 |
| DOUBLE       | 8字节                      | 双精度浮点数，精度比FLOAT高，取值范围更大                    | 同样存在精度丢失问题，只是出现的概率比FLOAT低，无法完全避免  | **同样禁止用于金额、价格存储**，适合存储对精度要求中等的非关键浮点数据，普通业务场景使用频率极低。 |
| DECIMAL(M,D) | 存储空间由精度M和标度D决定 | 精确定点数，以字符串的形式存储数字，**完全不会出现精度丢失问题** | 无精度风险，只要在定义的精度范围内，就能保证数字的绝对准确   | **全栈开发金额、价格、财务数据存储的唯一推荐类型**，所有和钱相关的字段，必须使用DECIMAL类型，绝对不能用FLOAT/DOUBLE。 |

#### DECIMAL类型参数详解
`DECIMAL(M,D)`中的两个参数定义如下：
- **M（精度）**：代表该数字总共能存储的有效数字位数，范围是1~65，默认值是10；
- **D（标度）**：代表小数点后面能存储的数字位数，范围是0~30，且不能大于M，默认值是0；
- 示例：`DECIMAL(10,2)`，代表总共最多10位有效数字，其中小数点后固定2位，能存储的最大值是`99999999.99`，完全覆盖绝大多数电商场景的商品价格、订单金额需求。

## 4.2 字符串类型
字符串类型是MySQL中使用频率最高的类型，用于存储文本数据，比如用户名、密码、手机号、地址、商品名称、文章内容、评论等，我们对所有核心字符串类型进行全面详解：
| 类型名称                          | 最大存储空间           | 核心特点                                                     | 全栈开发选型建议与适用场景                                   |
| --------------------------------- | ---------------------- | ------------------------------------------------------------ | ------------------------------------------------------------ |
| CHAR(M)                           | 0~255字节              | 定长字符串，M代表固定的字符长度，无论你实际存储的字符有多少，都会占用M个字符的存储空间。<br>优点：查询性能极高，写入速度快；<br>缺点：如果存储的内容长度远小于M，会造成存储空间浪费。 | **适合存储长度固定的文本数据**，全栈开发高频使用场景：<br>- 手机号：固定11位，定义为`CHAR(11)`；<br>- 身份证号：固定18位，定义为`CHAR(18)`；<br>- 固定长度的编码、状态码：比如6位的验证码，定义为`CHAR(6)`；<br>固定长度的文本使用CHAR类型，能获得极致的查询性能。 |
| VARCHAR(M)                        | 0~65535字节            | 变长字符串，M代表能存储的最大字符长度，仅占用实际存储内容的存储空间，不会浪费空间。<br>优点：节省存储空间，灵活度高；<br>缺点：查询性能略低于CHAR类型，对于超长文本性能一般。 | **全栈开发最核心、最常用的字符串类型**，适合存储长度不固定的文本数据，覆盖90%的业务文本场景：<br>- 用户名、昵称、邮箱：`VARCHAR(50)`；<br>- 收货地址、商品名称：`VARCHAR(255)`；<br>- 文章简介、评论内容：`VARCHAR(1000)`；<br>全栈开发规范：根据业务需求设置合理的最大长度，禁止盲目设置`VARCHAR(10000)`等过大的长度，避免性能损耗。 |
| TINYTEXT                          | 0~255字节              | 短文本类型，无需指定长度，最大存储255个字符                  | 使用频率极低，完全可以被VARCHAR(255)替代，不推荐使用         |
| TEXT                              | 0~65535字节            | 长文本类型，无需指定长度，最大存储65535个字符                | 适合存储中等长度的长文本，比如商品详情、文章摘要、长评论、富文本简介等，当文本长度超过VARCHAR的最大限制时，使用TEXT类型。 |
| MEDIUMTEXT                        | 0~16777215字节         | 中等长文本类型，最大存储约1600万个字符                       | 适合存储较长的文章内容、产品说明书、协议文本等大段文本内容。 |
| LONGTEXT                          | 0~4294967295字节       | 极大长文本类型，最大存储约4GB的文本数据                      | 适合存储超大文本内容，比如完整的小说章节、大体积的富文本内容、日志文本等，普通业务场景使用频率极低。 |
| TINYBLOB/BLOB/MEDIUMBLOB/LONGBLOB | 对应TEXT系列的存储空间 | 二进制字符串类型，用于存储二进制数据                         | 适合存储图片、音频、视频、文件等二进制数据，**全栈开发不推荐直接在数据库中存储二进制文件**，通常的做法是将文件存储在对象存储中，数据库只存储文件的访问地址，避免数据库体积过大、查询性能下降。 |

### 补充说明
- CHAR和VARCHAR中的M，代表的是**字符数**，不是字节数，比如`VARCHAR(50)`，无论是存储50个汉字，还是50个英文字母，都是允许的，无需担心中文占用多个字节的问题；
- 全栈开发规范：绝大多数文本场景，优先使用VARCHAR类型，根据业务需求设置合理的最大长度；固定长度的文本，优先使用CHAR类型，提升查询性能。

## 4.3 日期时间类型
日期时间类型用于存储时间相关的数据，比如用户注册时间、订单创建时间、商品上架时间、用户生日、操作日志时间等，是业务开发中必不可少的类型，我们进行全面详解：
| 类型名称  | 存储空间 | 格式                | 取值范围                                   | 核心特点                                                     | 全栈开发选型建议与适用场景                                   |
| --------- | -------- | ------------------- | ------------------------------------------ | ------------------------------------------------------------ | ------------------------------------------------------------ |
| DATE      | 3字节    | YYYY-MM-DD          | 1000-01-01 至 9999-12-31                   | 仅存储日期，不存储时间，占用空间极小                         | **全栈开发高频使用类型**，适合只需要日期、不需要时间的场景，比如用户生日、入职日期、商品生产日期、活动开始/结束日期等。 |
| TIME      | 3字节    | HH:MM:SS            | -838:59:59 至 838:59:59                    | 仅存储时间，不存储日期，支持超出24小时的时间范围             | 适合存储只需要时间、不需要日期的场景，比如店铺每日营业时间、任务执行时间、时长统计等，普通业务场景使用频率较低。 |
| YEAR      | 1字节    | YYYY                | 1901 至 2155                               | 仅存储年份，占用空间最小                                     | 适合只需要存储年份的场景，比如用户出生年份、商品生产年份、毕业年份等，使用频率较低。 |
| DATETIME  | 8字节    | YYYY-MM-DD HH:MM:SS | 1000-01-01 00:00:00 至 9999-12-31 23:59:59 | 同时存储日期和时间，取值范围极大，不受MySQL时区影响，数据不会随时区变化而改变 | **全栈开发最核心、最推荐的时间类型**，覆盖99%的业务时间存储场景：<br>- 用户注册时间、订单创建时间、操作日志时间；<br>- 商品上架时间、订单支付时间、内容发布时间；<br>优点是不受时区影响，取值范围大，没有2038年上限问题，是业务时间存储的首选。 |
| TIMESTAMP | 4字节    | YYYY-MM-DD HH:MM:SS | 1970-01-01 00:00:01 至 2038-01-19 03:14:07 | 时间戳类型，存储的是从1970年1月1日到当前时间的秒数，受MySQL时区影响，会随时区设置自动转换，有2038年的上限问题 | 适合存储和时区相关的时间，或者数据的更新时间，比如`update_time TIMESTAMP DEFAULT CURRENT_TIMESTAMP ON UPDATE CURRENT_TIMESTAMP`，可以实现数据更新时自动刷新时间；<br>**不推荐作为核心业务时间存储**，避免2038年上限问题和时区带来的异常。 |

### 全栈开发时间类型最佳实践
1. 绝大多数业务场景，时间字段统一使用`DATETIME`类型，避免时区问题和2038年上限问题；
2. 每张业务表，都建议强制添加两个固定的时间字段，这是全栈开发的通用规范：
   ```sql
   create_time DATETIME NOT NULL DEFAULT CURRENT_TIMESTAMP COMMENT '创建时间，插入数据时默认当前时间',
   update_time DATETIME NOT NULL DEFAULT CURRENT_TIMESTAMP ON UPDATE CURRENT_TIMESTAMP COMMENT '更新时间，数据修改时自动更新为当前时间'
   ```
3. 仅需要日期的场景，使用`DATE`类型，节省存储空间；
4. 禁止使用字符串类型存储时间数据，会导致日期计算、筛选、索引失效等一系列问题，必须使用对应的日期时间类型。

# 五、DDL-表操作-创建全解
掌握了数据类型之后，我们就可以开始创建数据表了，创建表是Python全栈项目开发的核心环节，表设计的好坏直接决定了后续接口开发的效率、项目的可维护性、数据查询的性能。本章节我们将全面讲解建表的完整语法、字段属性、入门示例、全栈开发建表规范，新手可以从最简示例入手，循序渐进掌握标准建表方法。

## 5.1 完整建表语法
```sql
CREATE TABLE [IF NOT EXISTS] 表名(
    字段1名 字段1数据类型 [字段属性] [COMMENT '字段1注释'],
    字段2名 字段2数据类型 [字段属性] [COMMENT '字段2注释'],
    字段3名 字段3数据类型 [字段属性] [COMMENT '字段3注释'],
    ......
    字段n名 字段n数据类型 [字段属性] [COMMENT '字段n注释']
)[ENGINE = 存储引擎] [DEFAULT CHARSET = 字符集] [COMMENT = '表注释'];
```

## 5.2 全语法参数详解
我们对建表语法的每一个部分进行全面、详细的讲解，新手不仅要会写语句，还要理解每一个部分的作用，写出符合规范的建表语句：

### 5.2.1 表级参数详解
| 参数                     | 是否必选               | 详细作用与使用说明                                           |
| ------------------------ | ---------------------- | ------------------------------------------------------------ |
| CREATE TABLE             | 必选                   | 创建表的固定关键字，语法固定，不可修改                       |
| IF NOT EXISTS            | 可选，推荐添加         | 防报错关键字，仅当该表名不存在时，才执行创建操作；如果表已存在，会跳过创建，不会抛出错误，避免表名冲突导致的报错。 |
| 表名                     | 必选                   | 自定义的表名称，全栈开发强制命名规范：<br>1. 仅使用小写英文字母、数字、下划线，禁止使用中文、特殊符号、空格；<br>2. 名称要体现业务含义，比如`user_info`、`order_info`、`goods`，禁止使用无意义的`t1`、`test`等名称；<br>3. 禁止使用MySQL关键字作为表名，比如`order`、`user`、`select`等，若必须使用，需要用反引号`` ` ``包裹；<br>4. 同一业务模块的表，建议使用统一前缀，比如电商系统的订单相关表，都以`order_`开头，方便管理。 |
| ENGINE = 存储引擎        | 可选，推荐指定         | 设置表的存储引擎，MySQL最常用的两个存储引擎：<br>1. **InnoDB**：MySQL 5.5之后的默认存储引擎，支持事务、行级锁、外键、崩溃恢复，是全栈开发的首选引擎，99%的业务场景都应该使用InnoDB；<br>2. **MyISAM**：不支持事务、仅支持表级锁，性能较差，已被淘汰，不推荐使用。<br>全栈开发规范：建表时强制指定`ENGINE = InnoDB`，明确表的存储引擎。 |
| DEFAULT CHARSET = 字符集 | 可选，推荐指定         | 设置表的默认字符集，推荐指定`utf8mb4`，如果创建数据库时已经指定了`utf8mb4`，表会默认继承数据库的字符集，无需重复指定；如果数据库未指定，建表时必须强制指定。 |
| COMMENT = '表注释'       | 可选，全栈开发强制要求 | 给表添加注释，明确说明这张表的业务作用、存储的内容，方便后续维护和团队协作，**全栈开发规范要求，每张表必须添加表注释**。 |

### 5.2.2 字段级参数详解
每个字段的定义格式为：`字段名 数据类型 [字段属性] [COMMENT '字段注释']`，我们对每个部分进行详解：
1. **字段名**：必选，字段的名称，命名规范和表名一致，使用小写英文字母、下划线，体现字段的业务含义，禁止使用关键字、中文；
2. **数据类型**：必选，给字段指定对应的数据类型，根据我们上一小章节讲解的选型规范，选择合适的类型和长度；
3. **字段属性**：可选，给字段添加额外的约束、属性，常用的字段属性如下：
   | 属性名称       | 作用说明                                                     | 使用场景                                                 |
   | -------------- | ------------------------------------------------------------ | -------------------------------------------------------- |
   | NOT NULL       | 非空约束，标识该字段不允许存储NULL值，插入数据时必须赋值     | 用户名、密码、手机号等必填字段，必须添加该属性           |
   | DEFAULT 默认值 | 给字段设置默认值，插入数据时如果没有给该字段赋值，会自动使用默认值填充 | 状态字段默认值0、性别字段默认值0、创建时间默认当前时间等 |
   | PRIMARY KEY    | 主键约束，标识该字段为表的主键，主键是每条数据的唯一标识，不能为空、不能重复，一张表只能有一个主键 | 每张表必须设置主键，通常用id字段作为主键                 |
   | AUTO_INCREMENT | 自增属性，只能配合整数类型的主键使用，插入数据时无需给该字段赋值，会自动从1开始递增，每次+1 | 主键id字段，通常都会添加该属性                           |
   | UNIQUE         | 唯一约束，标识该字段的所有值不能重复，比如用户名、手机号，不能有两条数据使用同一个值 | 用户名、手机号、邮箱等唯一标识的字段                     |
4. **COMMENT '字段注释'**：可选，全栈开发强制要求，给每个字段添加注释，明确说明字段的业务含义、枚举值的说明（比如1=男，2=女），**全栈开发规范要求，每个字段必须添加注释**。

### 5.2.3 语法核心注意事项
1. 多个字段之间用**英文逗号**分隔，**最后一个字段的末尾，绝对不能加逗号**，否则会报语法错误；
2. 所有符号必须是英文符号，禁止使用中文逗号、括号、引号；
3. 建表前必须先通过`USE 数据库名;`切换到对应的数据库中，否则表会创建到默认的数据库中。

# 六、DDL-表操作-修改全解
在Python项目的迭代过程中，业务需求会不断变化，经常需要对已有的表结构进行修改，比如新增字段、修改字段类型、重命名字段、删除字段、修改表名等，这些操作都通过`ALTER TABLE`语句实现，是后端开发日常工作中高频使用的操作。本章节我们对每一种表修改操作进行全面详解，包含完整语法、参数说明、极简示例、注意事项。

> 重要提示：表修改操作属于高危操作，尤其是生产环境，执行前必须先备份表结构和数据，先在测试环境验证通过后，再在生产环境执行，避免修改导致的业务异常。

## 6.1 给表添加新字段
当业务新增需求，需要存储新的信息时，就需要给已有的表添加新的字段，这是最常用的表修改操作。

### 完整语法
```sql
ALTER TABLE 表名 
ADD [COLUMN] 字段名 数据类型 [字段属性] [COMMENT '字段注释'] [FIRST|AFTER 已有字段名];
```

### 参数详解
| 参数                                         | 是否必选         | 详细作用与使用说明                                           |
| -------------------------------------------- | ---------------- | ------------------------------------------------------------ |
| `ALTER TABLE 表名`                           | 必选             | 修改表的固定关键字，后面跟要修改的表名                       |
| `ADD [COLUMN]`                               | 必选             | 添加字段的固定关键字，`COLUMN`是可选的，写和不写效果完全一致，`ADD 字段名`是更简洁的通用写法 |
| `字段名 数据类型 [字段属性][COMMENT '注释']` | 必选             | 新增字段的完整定义，语法和建表时的字段定义完全一致，包含类型、属性、注释 |
| `FIRST`                                      | AFTER 已有字段名 | 可选，如果是`FIRST`表示在第一个字段前插入，如果写了`AFTER 已有字段名的话`，表示该已有字段名的后面 |

### 示例合集
#### 示例1：最简新增字段

2. 生产环境给大表新增字段时，要避开业务高峰期，避免锁表导致的业务卡顿。

## 6.2 修改字段的数据类型和属性
当字段的类型、长度、属性无法满足业务需求时，我们可以修改字段的数据类型和属性，比如把name字段的长度从20修改为50，给字段添加非空约束、修改默认值等。

### 完整语法
```sql
ALTER TABLE 表名
MODIFY [COLUMN] 字段名 新的数据类型 [字段属性] [COMMENT '字段注释'] [FIRST|AFTER 已有字段名];
```

### 参数详解
- `MODIFY`是修改字段类型和属性的固定关键字，其他参数的含义和新增字段完全一致；
- 该语句可以修改字段的类型、长度、属性、注释、在表中的位置，唯一不能修改的是字段名（修改字段名需要用CHANGE关键字）。

### 示例合集
#### 示例1：修改字段长度
```sql

ALTER TABLE user_info
```

### 新手避坑指南
1. 修改字段类型时，要注意数据兼容性，比如把VARCHAR类型修改为INT类型，如果字段中已经有非数字的内容，会修改失败；
2. 缩小字段长度时，要先确认表中已有数据的长度，比如已有地址已经有200个字符，把字段长度修改为100，会修改失败；
3. 给已有数据的字段添加`NOT NULL`非空约束时，必须先给该字段设置默认值，或者给所有已有数据的该字段赋值，否则会修改失败。

## 6.3 修改字段名和字段类型

# 七、DDL-表操作-删除全解
删除表是高危操作，会直接删除表的完整结构、表中的所有业务数据、索引、约束，且**几乎无法恢复**，新手仅可在本地测试环境练习使用，生产环境必须有严格的审批与备份流程，绝对禁止随意执行。本章节我们讲解两种表删除方式：`DROP TABLE`删除整张表、`TRUNCATE TABLE`清空表数据，同时详解两者的核心区别、使用场景与风险管控规范。

## 7.1 DROP TABLE：删除整张表
该语句会彻底删除整张表，包括表的结构定义、所有数据、索引、约束、触发器，删除后这张表就完全不存在了，相当于把仓库里的整个货架连带上面的所有物品一起彻底拆除。

### 完整语法
```sql
DROP TABLE [IF EXISTS] 表名1, 表名2, ...;
```

### 参数详解
| 参数       | 是否必选           | 详细作用与使用说明                                           |
| ---------- | ------------------ | ------------------------------------------------------------ |
| DROP TABLE | 必选               | 删除表的固定关键字                                           |
| IF EXISTS  | 可选，强烈推荐添加 | 防报错关键字，仅当表存在时才执行删除操作，表不存在时不会抛出错误；不添加该参数时，表不存在会直接报错。 |
| 表名       | 必选               | 要删除的表名称，支持同时删除多个表，多个表名之间用英文逗号分隔。 |

### 极简示例
#### 示例1：删除单张表
```sql
-- 安全删除test表，仅当表存在时执行删除
DROP TABLE IF EXISTS test;
```

![在这里插入图片描述](https://i-blog.csdnimg.cn/direct/2b33ba5a6bb74cfb8182a2f679cad0d2.png#pic_center)


#### 示例2：同时删除多张表

```sql
-- 同时删除test1、test2、test3三张表
DROP TABLE IF EXISTS test1, test2, test3;
```

## 7.2 TRUNCATE TABLE：清空表中所有数据，保留表结构
该语句不会删除表本身，只会清空表中的所有数据，表的结构、字段、约束、索引都会完整保留，相当于把货架上的所有物品全部清空，货架本身还留在仓库里，可以继续往里面放东西。

### 完整语法
```sql
TRUNCATE TABLE 表名;
```

### 极简示例
```sql
-- 清空student表中的所有数据，表结构完整保留
TRUNCATE TABLE student;
```

### 补充说明
`TRUNCATE TABLE`的执行原理是直接删除并重建表，执行速度极快，尤其是清空大表时，比`DELETE FROM 表名;`（DML语句）效率高得多，但是它无法指定删除条件，只能清空整张表的所有数据。

## 7.3 DROP、TRUNCATE、DELETE的核心区别
很多新手会混淆这三个删除操作，我们用一张表清晰地对比三者的核心区别，明确不同场景该用哪个操作：
| 操作语句         | 操作类型 | 表结构是否保留     | 数据是否可恢复     | 执行速度             | 是否可加WHERE条件                 | 事务回滚     | 风险等级 |
| ---------------- | -------- | ------------------ | ------------------ | -------------------- | --------------------------------- | ------------ | -------- |
| DROP TABLE       | DDL      | 不保留，表彻底删除 | 几乎无法恢复       | 极快                 | 不支持                            | 无法回滚     | 极高     |
| TRUNCATE TABLE   | DDL      | 保留，仅清空数据   | 几乎无法恢复       | 极快                 | 不支持                            | 无法回滚     | 高       |
| DELETE FROM 表名 | DML      | 保留，仅删除数据   | 可通过事务回滚恢复 | 慢，大表删除效率极低 | 支持，可通过WHERE条件删除指定数据 | 支持事务回滚 | 中       |

## 7.4 全栈开发表删除操作红线规范
1. **生产环境绝对红线**：生产环境禁止直接执行`DROP TABLE`和`TRUNCATE TABLE`语句，除非有完整的业务下线审批、全量数据备份、回滚方案，否则绝对禁止执行；
2. **操作前强制备份**：无论什么环境，执行表删除、清空操作前，必须对该表进行全量备份，确认备份可用后再执行操作；
3. **权限管控**：生产环境的数据库账号，绝对不能给普通开发者分配删表、清空表的权限，仅DBA可拥有该权限，从根源上规避误删风险；
4. **逻辑删除替代物理删除**：全栈开发规范中，业务数据不做物理删除（DELETE/DROP/TRUNCATE），而是使用逻辑删除，也就是通过`is_delete`字段标识数据是否删除，0=未删除，1=已删除，既保留了历史数据，又实现了删除效果，避免数据丢失；
5. **新手练习限制**：新手仅可在本地测试环境，删除自己创建的测试表，绝对不要操作业务表和系统表。

# 八、Python全栈开发DDL最佳实践
在Python全栈项目开发中，DDL操作不仅是建库建表的技术操作，更是影响项目可维护性、稳定性、团队协作效率的核心环节，这里我们总结了全栈开发中DDL操作的行业通用最佳实践，新手从一开始就要养成规范的开发习惯。

## 8.1 库表设计命名规范
1. **统一命名风格**：所有库名、表名、字段名，全部使用**小写英文字母+数字+下划线**命名，禁止使用中文、特殊符号、空格、驼峰命名；
2. **见名知意**：库名、表名、字段名必须体现业务含义，禁止使用`db1`、`t1`、`a`、`b`等无意义的名称；
3. **禁止使用关键字**：绝对禁止使用MySQL的关键字、保留字作为库名、表名、字段名，比如`order`、`user`、`select`、`delete`等；
4. **统一前缀规范**：同一业务模块的表，使用统一的前缀，比如订单模块的表都以`order_`开头，用户模块的表都以`user_`开头，方便表的管理和维护；
5. **通用字段规范**：所有业务表都强制添加`id`（主键）、`create_time`（创建时间）、`update_time`（更新时间）、`is_delete`（逻辑删除标识）四个通用字段，形成统一的表结构规范。

## 8.2 字段设计规范
1. **合适的类型与长度**：为每个字段选择最合适的数据类型和长度，在满足业务需求的前提下，尽量使用更小的类型，比如能用TINYINT就不用INT，能用VARCHAR(50)就不用VARCHAR(255)，节省存储空间，提升查询性能；
2. **金额字段强制使用DECIMAL**：所有和钱相关的金额、价格字段，必须使用DECIMAL类型，绝对禁止使用FLOAT、DOUBLE类型，避免精度丢失；
3. **时间字段优先使用DATETIME**：业务时间字段优先使用DATETIME类型，避免TIMESTAMP的2038年问题和时区影响；
4. **尽量设置非空约束**：除了少数允许为空的字段，其他字段尽量设置`NOT NULL`非空约束，并设置合理的默认值，避免NULL值带来的查询性能、索引失效问题；
5. **每个字段必须加注释**：所有表、所有字段必须添加清晰的注释，枚举值必须在注释中说明（比如1=男，2=女），方便团队协作和后续维护。

## 8.3 多环境DDL操作规范
1. **版本化管理**：项目的所有DDL语句，都必须写入SQL文件，纳入Git版本管理，记录每一次表结构的变更，方便多环境同步和版本回滚；
2. **环境隔离**：开发、测试、生产环境严格分离，DDL变更必须先在开发环境编写、测试，再同步到测试环境验证，最后才能在生产环境执行，绝对禁止直接在生产环境写DDL语句；
3. **变更审批**：生产环境的表结构变更、删除操作，必须走审批流程，提交变更SQL、影响范围、回滚方案，审批通过后才能执行；
4. **全量备份**：生产环境执行任何DDL变更前，必须对相关的库表进行全量备份，确保变更出现问题时可以快速回滚。

## 8.4 性能与安全规范
1. **生产环境大表变更避峰**：生产环境对大表执行DDL变更时，必须避开业务高峰期，避免锁表导致的业务卡顿、不可用；
2. **最小权限原则**：数据库账号遵循最小权限原则，开发、测试环境的账号仅分配必要的权限，生产环境的业务账号仅分配DML、DQL权限，绝对不分配DDL、DCL权限；
3. **禁止物理删除**：业务数据优先使用逻辑删除，禁止随意使用物理删除，避免数据丢失无法恢复；
4. **禁止随意修改、删除表结构**：项目上线后，禁止随意修改、删除表结构、字段，所有变更必须有对应的业务需求和完整的测试。

# 九、新手DDL操作常见报错与解决方案
新手在DDL操作过程中，90%的报错都集中在以下场景，我们整理了常见报错的根因分析与详细解决方案，新手遇到报错可以直接对照排查。

---

### 报错1：`You have an error in your SQL syntax; check the manual that corresponds to your MySQL server version for the right syntax to use near '...'`
#### 根因分析
SQL语法错误，这是新手最常见的报错，99%的情况是以下几种原因：
1. 使用了中文的逗号、分号、括号、引号等符号；
2. 建表语句中，最后一个字段的末尾加了逗号；
3. 关键字拼写错误，比如把`CREATE`写成`CREAT`，把`DATABASE`写成`DATASBASE`；
4. 使用了MySQL的关键字作为库名、表名、字段名，且没有用反引号包裹。

#### 解决方案
1. 检查SQL语句中的所有符号，确保全部是英文符号；
2. 检查建表语句，确认最后一个字段末尾没有逗号；
3. 核对SQL关键字的拼写，确保没有拼写错误；
4. 检查库名、表名、字段名是否使用了关键字，要么修改名称，要么用反引号`` ` ``包裹。

---

### 报错2：`No database selected`
#### 根因分析
执行表相关的操作时，没有通过`USE 数据库名;`切换到对应的数据库，MySQL不知道要操作哪个数据库里的表。

#### 解决方案
执行表操作前，先执行`USE 数据库名;`切换到对应的数据库，再执行表相关的语句。

---

### 报错3：`Can't create database 'xxx'; database exists`
#### 根因分析
创建数据库时，没有加`IF NOT EXISTS`，且该数据库名称已经存在。

#### 解决方案
1. 先通过`SHOW DATABASES;`确认数据库是否已存在；
2. 建库语句加上`IF NOT EXISTS`，避免重复创建报错。

---

### 报错4：`Unknown database 'xxx'`
#### 根因分析
执行`USE 数据库名;`或者操作数据库时，该数据库不存在，要么是数据库名拼写错误，要么是还没创建该数据库。

#### 解决方案
1. 核对数据库名的拼写，确保没有写错；
2. 通过`SHOW DATABASES;`确认数据库是否存在，不存在的话先创建数据库。

---

### 报错5：`Table 'xxx' already exists`
#### 根因分析
创建表时，没有加`IF NOT EXISTS`，且该表名在当前数据库中已经存在。

#### 解决方案
1. 先通过`SHOW TABLES;`确认表是否已存在；
2. 建表语句加上`IF NOT EXISTS`，避免重复创建报错。

---

### 报错6：`Unknown column 'xxx' in 'field list'`
#### 根因分析
修改、查询字段时，字段名拼写错误，或者该字段在表中不存在。

#### 解决方案
1. 通过`DESC 表名;`查看表的字段列表，核对字段名的拼写是否正确；
2. 确认该字段是否已经创建，若不存在先执行新增字段的操作。

---

### 报错7：`Data truncated for column 'xxx' at row 1`
#### 根因分析
修改字段类型、长度时，表中已有数据超出了新类型/新长度的范围，比如把VARCHAR(200)修改为VARCHAR(100)，但表中已有数据的长度超过了100。

#### 解决方案
1. 先清理表中超出长度的数据，或者调整字段的长度，确保能容纳所有已有数据；
2. 修改字段类型前，先确认已有数据和新类型的兼容性。

---

### 报错8：`Access denied for user 'xxx'@'xxx' to database 'xxx'`
#### 根因分析
当前使用的数据库账号，没有执行对应DDL操作的权限，比如没有建库、建表、修改表的权限。

#### 解决方案
1. 联系数据库管理员，给账号分配对应的操作权限；
2. 核对账号是否正确，是否使用了权限不足的账号。

# 十、核心总结：DDL全量语法速查表
为了方便学习、开发时快速查阅，我们整理了DDL全量核心语法速查表，覆盖所有基础操作：
| 操作类型        | 核心SQL语法                                                  | 核心功能                                 |
| --------------- | ------------------------------------------------------------ | ---------------------------------------- |
| 数据库-查询所有 | `SHOW DATABASES;`                                            | 查看当前MySQL服务中所有的数据库          |
| 数据库-查询当前 | `SELECT DATABASE();`                                         | 查看当前所在的数据库                     |
| 数据库-创建     | `CREATE DATABASE [IF NOT EXISTS] 库名 [DEFAULT CHARSET utf8mb4][COLLATE utf8mb4_general_ci];` | 创建新的数据库                           |
| 数据库-删除     | `DROP DATABASE [IF EXISTS] 库名;`                            | 删除数据库（高危操作）                   |
| 数据库-切换     | `USE 库名;`                                                  | 切换到指定的数据库                       |
| 表-查询所有     | `SHOW TABLES;`                                               | 查看当前数据库中所有的表                 |
| 表-查询结构     | `DESC 表名;`                                                 | 查看表的字段结构详情                     |
| 表-查询建表语句 | `SHOW CREATE TABLE 表名;`                                    | 查看表的完整建表SQL语句                  |
| 表-创建         | `CREATE TABLE [IF NOT EXISTS] 表名(字段名 类型 [属性][COMMENT '注释'],...)[ENGINE=InnoDB][DEFAULT CHARSET=utf8mb4] [COMMENT '表注释'];` | 创建新的数据表                           |
| 表-新增字段     | `ALTER TABLE 表名 ADD 字段名 类型 [属性][COMMENT '注释'] [AFTER 已有字段名];` | 给表添加新的字段                         |
| 表-修改字段类型 | `ALTER TABLE 表名 MODIFY 字段名 新类型 [属性][COMMENT '注释'];` | 修改字段的类型、属性、注释               |
| 表-修改字段名   | `ALTER TABLE 表名 CHANGE 旧字段名 新字段名 类型 [属性][COMMENT '注释'];` | 修改字段的名称、类型、属性               |
| 表-删除字段     | `ALTER TABLE 表名 DROP 字段名;`                              | 删除表中的字段（高危操作）               |
| 表-修改表名     | `ALTER TABLE 旧表名 RENAME TO 新表名;`                       | 修改表的名称                             |
| 表-删除整张表   | `DROP TABLE [IF EXISTS] 表名;`                               | 彻底删除整张表（高危操作）               |
| 表-清空表数据   | `TRUNCATE TABLE 表名;`                                       | 清空表中所有数据，保留表结构（高危操作） |
